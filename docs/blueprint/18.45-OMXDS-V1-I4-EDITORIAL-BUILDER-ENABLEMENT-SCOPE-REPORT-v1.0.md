## 1. Decisión

I4 evolucionará el Experience Builder existente; no creará un segundo Builder, una fuente de verdad paralela ni rutas públicas nuevas. La fase se divide en cinco lotes cerrados —I4-0, I4-A, I4-B, I4-C e I4-D— para separar contrato, seguridad de autoría, workflow, operación y aceptación integral.

La arquitectura conserva `page_compositions`, `page_revisions`, `VisualStudio`, `CompositionRenderer`, Block Library/Registry, preview por token y las RPC existentes como activos a endurecer. Ningún lote podrá reemplazarlos por una solución paralela ni usar el Builder para alterar datos gobernados, elegibilidad Premium, comercio, rutas, canonical o permisos.

La aprobación de este Scope Report sólo permite preparar una autorización posterior de I4-0 sobre su lista cerrada. No concede permiso para modificar ninguna ruta técnica aquí identificada.

## 2. Behavioral Change Statement

El Builder pasará de una biblioteca extensible con permisos y transiciones parcialmente coordinados a un sistema contractual fail-closed: sólo podrá ofrecer autoría registrada, separar narrativa de datos gobernados, exigir estados y actores válidos, detectar conflictos, producir evidencia auditable y restaurar versiones sin revivir datos vencidos.

El visitante no deberá percibir cambios durante I4-0 ni I4-A con el flag público vigente en `false`. Preview seguirá sin equivaler a publicación. Ningún lote de I4 habilita Premium, comercio, reservaciones, Zazil Tunich ni exposición pública.

## 5. Arquitectura objetivo de I4

I4 añade una capa de policy común sobre el Builder existente:

1. **Contract Registry:** identidad y versión de templates, regiones, slots, bloques, fields y variantes.
2. **Authoring Policy:** allowlist por superficie/rol, modo de autoría y compatibilidad legacy.
3. **Source Policy:** clasificación `editorial`, `reference`, `media`, `governed`, `calculated`, `system` o `legal`; el Builder sólo escribe las clases autorizadas.
4. **Workflow Authority:** transiciones, actor, snapshot/hash aprobado y autorización server-side.
5. **Preview Boundary:** token, expiración, noindex, aislamiento y cero efectos de publicación/comercio.
6. **Concurrency Authority:** versión/hash esperado; ningún save silencioso cuando el draft cambió.
7. **Audit Authority:** quién, qué, cuándo, fuente, versión, resultado y motivo de rechazo.
8. **Rollback Authority:** restauración a nuevo draft y revalidación de contratos/fuentes actuales antes de publicar.

Las validaciones críticas deberán existir en la frontera server/DB aplicable. La UI sólo explica el resultado; nunca será el control de seguridad.

## 6. Allowlist y procedencia

### 6.1 Modos de bloque

Todo tipo registrado resolverá exactamente uno de estos modos:

| Modo                 |      Nueva inserción       |           Edición           |    Render legacy    |            Publicación nueva            |
| -------------------- | :------------------------: | :-------------------------: | :-----------------: | :-------------------------------------: |
| `authorable`         |  sí, dentro del contrato   |             sí              |         sí          |             sí, tras gates              |
| `governed_read_only` | seleccionable como binding | sólo presentación permitida |         sí          |       sí, si la fuente es vigente       |
| `legacy_read_only`   |             no             |             no              | sí, con advertencia | sólo composición histórica ya publicada |
| `prohibited`         |             no             |             no              |         no          |                   no                    |

`vmx.custom.html` queda fijado como `legacy_read_only`: se rechazan inserción, duplicación, edición, IA, template nuevo y promoción a Premium. Su render histórico se conserva temporalmente para no romper composiciones ya publicadas. La eliminación física requiere inventario cero o migración aprobada y no pertenece a I4-0.

### 6.2 Fields

Cada field deberá declarar clase, tipo, límites, traducción, procedencia, roles de escritura y estrategia de fallback. Tipos, opciones, cardinalidad, URLs y referencias se validan tanto al insertar como al guardar y publicar. Campos desconocidos producen rechazo; no se conservan silenciosamente.

### 6.3 Fuentes gobernadas

Rating, premios, certificaciones, precio, moneda, inventario, disponibilidad, horario, estado abierto/cerrado, geografía, canonical, publicación, permisos y elegibilidad Premium son sólo lectura. El editor puede ubicar una presentación elegible; no puede escribir el valor ni sustituirlo con copy contradictorio.

La allowlist de fuentes se limita a readers/RPC/tablas previamente autorizados y registrados. No se admiten tabla, columna, query, URL, iframe, webhook o reader escritos libremente desde el Studio.

## 7. Lotes de implementación

### 7.1 I4-0 · Shared Editorial Builder Contract

**Objetivo:** crear el contrato/policy interno ejecutable y su harness, sin conectarlo a consumidores.

**Dentro:** vocabulario de modos, clases de field, decisiones de allowlist, conflictos de fuentes, workflow, preview, concurrencia, auditoría y rollback; fixtures ficticios; pruebas contractuales y evidence gate; registro de comandos.

**Fuera:** `VisualStudio`, Block Library activa, renderer, rutas, RPC, schema, migraciones, datos, flags, UI, producción y cualquier consumidor público.

**Salida:** contrato puro reusable y evidencia de que no tiene imports desde rutas/componentes ni cambia comportamiento.

### 7.2 I4-A · Authoring Allowlist & Legacy Confinement

**Objetivo:** conectar la policy al Registry/Library/Studio y bloquear nuevas inserciones inseguras, preservando lectura legacy.

**Dentro:** filtrado por modo/superficie/rol; rechazo server-side al guardar árboles con nodos no autorizados; `vmx.custom.html` oculto y no insertable/duplicable/editable; validación de fields, URLs, referencias y fuentes.

**Fuera:** borrar renderer legacy, migrar composiciones, cambiar rutas públicas, workflow, Premium o datos gobernados.

**Salida:** EBG-01–04 y SEC-07 automatizados; composiciones legacy renderizan sin habilitar nueva autoría.

### 7.3 I4-B · Workflow, RBAC & Publication Authority

**Objetivo:** hacer atómico y server-authoritative el ciclo Draft→Review→Approved→Published.

**Dentro:** transiciones cerradas; snapshot/hash aprobado; invalidación por edición; separación autor–aprobador; publicación sólo del snapshot exacto aprobado; aislamiento por entidad; retiro y programación con las mismas reglas.

**Fuera:** self-publishing comercial, roles nuevos generales, rutas, Commerce, Premium o exposición pública del piloto.

**Salida:** EBG-05–09, SEC-01–03/05/09 con casos positivos y negativos.

### 7.4 I4-C · Preview, Concurrency, Audit & Rollback

**Objetivo:** cerrar operación segura y reversible del flujo editorial.

**Dentro:** preview aislado y noindex; tokens expirables/revocables; compare-and-swap de versión/hash; conflicto explícito; auditoría completa; rollback a nuevo draft con revalidación de fuentes actuales; timezone `America/Merida` donde se muestre tiempo operativo.

**Fuera:** publicación pública, analítica productiva nueva, P0/P1 o activación de flags.

**Salida:** EBG-10–13, ANA-09, SEO-10/11, SEC-04/08/09 y pruebas de recuperación.

### 7.5 I4-D · G3 Integration & Evidence Closure

**Objetivo:** ejecutar el slice vertical completo en entorno no público y cerrar G3.

**Dentro:** un bloque editorial authorable, un binding gobernado read-only, preview, Draft→Published, conflicto, auditoría y rollback; responsive 390/768/1024/1440; zoom/reflow, teclado, lector, touch, Sol/Luna, seguridad y evidencia integral.

**Fuera:** migración Premium, Zazil Tunich, publicación controlada, producción, Commerce, P0, P1 o L1.

**Salida:** G3 `PASS` con cero P0/P1. `PASS WITH CONDITIONS` no habilita P1 ni publicación.

## 8. Dependencias y orden

Orden obligatorio: `I4-0 → I4-A → I4-B → I4-C → I4-D`.

- I4-A depende del contrato I4-0 estable.
- I4-B depende de que árboles nuevos ya sean validables por allowlist.
- I4-C depende de identidad de versión/snapshot definida por I4-B.
- I4-D no corrige arquitectura; integra y demuestra.
- cualquier migración se crea sólo en el lote que la necesita y con rollback/compatibilidad explícitos;
- cada lote usa base exacta, PCA propia cuando toque rutas protegidas, allowlist, conteo y árbol aprobados;
- ningún lote hereda autorización para el siguiente.

## 10. Matriz mínima de pruebas G3

| Área         | Positivas obligatorias                                                    | Negativas obligatorias                                                                    |
| ------------ | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Allowlist    | insertar bloque/field/variante registrado y compatible                    | desconocido, superficie/rol incorrecto, field extra, URL/query libre                      |
| HTML legacy  | composición publicada histórica renderiza read-only                       | insertar, duplicar, editar, IA o template nuevo con `vmx.custom.html`                     |
| Fuentes      | seleccionar binding gobernado vigente y renderizarlo                      | escribir rating/precio/horario/geo/disponibilidad o contradecir fuente                    |
| Workflow     | autor envía, otro actor aprueba, publisher autorizado publica hash exacto | saltar estado, autoaprobar, publicar draft/revisión vieja o editar aprobado sin invalidar |
| RBAC         | actor autorizado actúa sólo sobre su alcance                              | empresa/rol ajeno modifica entidad, medios, premio o composición ajena                    |
| Preview      | token válido muestra draft noindex sin mutar estado                       | token vencido/revocado, fuga, indexación, comercio o publicación por preview              |
| Concurrencia | save con versión esperada avanza                                          | versión/hash obsoleto produce conflicto; nunca last-write-wins silencioso                 |
| Auditoría    | registra actor, diff, fuente, versión y resultado                         | rol editorial altera/borra log o rechazo queda sin evidencia                              |
| Rollback     | crea nuevo draft desde revisión y revalida fuentes actuales               | revive binding vencido, cambia URL/entidad o publica automáticamente                      |
| Regresión    | flag OFF y rutas públicas conservan HTML/SEO/CTA vigentes                 | nuevo import público, nueva ruta, dependencia, schema o dato fuera de alcance             |

Además son obligatorios lint L1, I1, I2-A/B/C, I3-0/A/B/C/D, typecheck, build, sincronización de gobernanza, Governance Integrity, Product Authorization Gate, change-package gate y pruebas propias del lote. I4-D añade pruebas humanas de teclado, lector, touch, zoom 200 % y viewports definidos.

## 12. Condiciones de parada

El lote activo regresa a Founder Review si:

- requiere una ruta, migración, dependencia, flag, rol, tabla, RPC o endpoint no autorizado;
- el árbol, conteo, base o commit difieren de lo aprobado;
- aparece una composición legacy que no puede preservarse sin nueva autoría insegura;
- una validación sólo puede hacerse en UI y no en la autoridad server/DB correspondiente;
- el flag OFF altera rutas públicas o reabre una capacidad insegura;
- una prueba P0/P1 falla, se omite o se sustituye por inspección informal;
- se necesita dato real, medio, Premium, Commerce, Zazil Tunich o producción;
- el sincronizador deriva rutas ajenas o una fuente gobernada exige corrección manual.
