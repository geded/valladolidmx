## 1. Decisión Founder

Founder autoriza exclusivamente construir el contrato interno compartido de I4-0 y su harness reproducible sobre la base exacta. El lote define allowlists ejecutables y fronteras fail-closed, pero no conecta la policy con Studio, Block Library, Registry activo, renderer, rutas, RPC, base de datos, migraciones, flags o consumidores públicos.

I4-0 no cambia el comportamiento del visitante ni habilita el Builder. Su salida es una autoridad pura que los lotes posteriores podrán consumir únicamente después de una autorización separada.

## 2. Behavioral Change Statement

Antes de I4-0, las reglas editoriales aprobadas estaban distribuidas entre documentos y metadata parcial del Block Contract. Después de I4-0 existe una representación TypeScript única, determinista y comprobable de modos, bloques, fields, variantes, fuentes, workflow, preview, concurrencia, auditoría y rollback.

La policy no se conecta todavía al producto. Por ello, el cambio observable para visitante, editor y empresa es exactamente cero. La ganancia es arquitectónica: I4-A ya no podrá inventar permisos o excepciones desde la UI; deberá consumir un contrato cerrado o fallar.

## 4. Contrato implementado

### 4.1 Modos de bloque

| Modo                 |      Autoría nueva      |     Edición      |           Binding           | Render histórico |                     Publicación nueva                     |
| -------------------- | :---------------------: | :--------------: | :-------------------------: | :--------------: | :-------------------------------------------------------: |
| `authorable`         | sí, dentro de allowlist |        sí        |   por fields registrados    |    no aplica     | declarativamente elegible; gates posteriores obligatorios |
| `governed_read_only` |  no como valor manual   | no sobre el dato | sí, desde fuente registrada |    no aplica     |             elegible sólo con fuente vigente              |
| `legacy_read_only`   |           no            |        no        |             no              |        sí        |                            no                             |
| `prohibited`         |           no            |        no        |             no              |        no        |                            no                             |

`vmx.custom.html` queda registrado exactamente como `legacy_read_only`. Su única operación permitida es `render_legacy`. Se rechazan inserción, edición, duplicación, IA, template nuevo, binding y publicación nueva. La policy no elimina ni modifica el renderer histórico; esa frontera pertenece a I4-A y posteriores.

### 4.2 Clases de field

La allowlist reconoce exclusivamente:

- `editorial`: texto estructurado, limitado, traducible y versionado;
- `reference`: selección de una entidad elegible;
- `media`: selección desde Media Registry;
- `governed`: verdad operativa de sólo lectura;
- `calculated`: valor producido por servicio autorizado;
- `system`: canonical, estado, permisos o identidad de plataforma;
- `legal`: contenido sujeto a autoridad especializada.

Las clases `governed`, `calculated`, `system` y `legal` no declaran escritores editoriales. Todo field desconocido se rechaza; no se conserva silenciosamente.

### 4.3 Bloques, variantes y superficies

El registro contractual aislado admite inicialmente:

| Block type                    | Modo                 | Familia    | Variantes                         |
| ----------------------------- | -------------------- | ---------- | --------------------------------- |
| `vmx.hero`                    | `authorable`         | identity   | `default`, `media_left`           |
| `vmx.rich-narrative`          | `authorable`         | narrative  | `default`, `chapter`, `quote_led` |
| `vmx.gallery`                 | `authorable`         | media      | `grid`, `carousel_accessible`     |
| `vmx.governed.practical-info` | `governed_read_only` | operations | `compact`, `detailed`             |
| `vmx.governed.trust-signals`  | `governed_read_only` | trust      | `summary`, `badges`               |
| `vmx.custom.html`             | `legacy_read_only`   | legacy     | `legacy`                          |

Cada entrada restringe superficies, actores, fields, fuentes y variantes. Este catálogo no modifica `INITIAL_BLOCK_LIBRARY`, `block-registry.ts` ni ningún consumidor activo.

### 4.4 Fuentes gobernadas

Sólo se aceptan estos identificadores cerrados:

`routing.canonical`; `geography.location`; `operations.schedule`; `commerce.price`; `commerce.availability`; `reputation.rating`; `trust.badges`; `publication.state`; `premium.eligibility`; `media.registry`.

No se permite escribir tabla, columna, query, URL, iframe, webhook o reader libre desde el contrato. I4-0 sólo declara identidad y precedencia; no ejecuta lecturas.

## 5. Workflow y separación de funciones

El vocabulario cerrado es `draft`, `in_review`, `changes_requested`, `approved`, `scheduled`, `published`, `unpublished` y `archived`.

La policy exige:

1. transiciones explícitamente registradas;
2. autor y aprobador distintos al aprobar;
3. aprobación vinculada al hash exacto del snapshot;
4. invalidación de aprobación después de editar;
5. publicación o programación sólo cuando el snapshot actual coincide con el aprobado.

I4-0 valida el contrato puro. La autoridad server-side y la persistencia atómica se implementarán únicamente en I4-B con autorización separada.

## 6. Preview, concurrencia, auditoría y rollback

### Preview

- temas `sol` y `luna`;
- viewports `390`, `768`, `1024` y `1440`;
- token expirable y `noindex` obligatorios;
- incapacidad explícita para publicar o mutar Commerce.

### Concurrencia

- versión esperada obligatoria;
- hash esperado obligatorio;
- `silent last-write-wins` prohibido.

### Auditoría

La evidencia futura será inmutable y deberá contener `actor`, `action`, `source`, `version`, `result` y `occurred_at`.

### Rollback

- restaura como nuevo Draft;
- revalida las fuentes gobernadas vigentes;
- nunca publica automáticamente.

Estas reglas son invariantes contractuales. I4-0 no crea tablas, RPC, tokens o logs.

## 7. Extensión compatible de Block Contract

`block-contract.ts` añade metadata opcional de field y bloque. Los contratos existentes que no declaran metadata I4-0 conservan su resultado exacto. Cuando un contrato futuro sí la declare, el validador rechaza:

- modo o clase desconocidos;
- variantes vacías o duplicadas;
- fuente fuera de allowlist;
- field inexistente;
- escritor sobre clase de sólo lectura.

La metadata opcional no importa el registro canónico ni activa automáticamente ningún bloque.

## 9. Pruebas positivas

- policy canónica válida y vocabularios cerrados;
- Hero ficticio con bloque, superficie, actor, variante, fields y fuente permitidos;
- binding gobernado ficticio sin escritura manual;
- `vmx.custom.html` renderizable sólo como legado;

## 10. Pruebas negativas

- block type desconocido;
- variante, field, actor, superficie o fuente fuera de allowlist;
- longitud editorial excedida;
- escritura manual de horario, geografía, rating o badges;
- inserción, edición, duplicación, IA, template, binding o publicación nueva de `vmx.custom.html`;
- autoaprobación;
- transición no registrada;
- publicación de hash distinto al aprobado;
- preview con capacidad de publicar o mutar Commerce;
- last-write-wins silencioso;
- rollback que publique o evite revalidar fuentes;
- metadata de sólo lectura con escritores;
- import de la policy desde cualquier consumidor de `src/` fuera de los dos contratos autorizados.
