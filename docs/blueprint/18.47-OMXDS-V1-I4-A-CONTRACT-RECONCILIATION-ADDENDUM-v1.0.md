## 1. Decisión propuesta

I4-A no conectará literalmente los seis identificadores conceptuales de I4-0 al catálogo activo. Antes deberá reconciliarlos con los `BlockContract` oficiales ya registrados, manteniendo una única identidad runtime por familia y sin crear aliases persistidos, bloques paralelos, rutas o fuentes nuevas.

La reconciliación adopta cuatro decisiones fail-closed:

1. las familias oficiales `vmx.experience.*` serán las identidades runtime de la primera allowlist editorial;
2. los tipos registrados que no queden expresamente admitidos no aparecerán para nueva autoría y sólo podrán atravesar un guardado si ya existían y permanecen idénticos;
3. `vmx.custom.html` conservará exclusivamente su render histórico y quedará bloqueado para inserción, edición, movimiento, duplicación, IA, reutilización y templates nuevos;
4. I4-A no admitirá enlaces o embeds externos nuevos: la allowlist externa inicial será vacía y sólo se aceptarán referencias canónicas internas o assets del Media Registry.

Este addendum resuelve el desacople detectado por el preflight, pero no implementa la solución ni concede autorización para modificar las quince rutas candidatas.

## 3. Hallazgo que origina el addendum

El preflight sobre la base exacta confirmó:

- la policy aislada contiene seis tipos conceptuales;
- `block-library.ts` contiene al menos 48 declaraciones literales `vmx.*`, además de contratos incorporados mediante spreads;
- sólo `vmx.hero` y `vmx.custom.html` coinciden literalmente entre la policy y el catálogo inspeccionado;
- incluso `vmx.hero` difiere en fields y variantes: la policy declara `heading`, `summary`, `media` y `canonical_target`, mientras el contrato activo usa `title`, `subtitle`, `background_images`, `ctas` y controles de presentación;
- `VisualStudio` consulta el Registry completo y el modal de Library filtra actualmente como superficie `home`;
- `saveCompositionDraft` persiste el árbol después de traducción best-effort sin validación I4;
- `duplicateComposition` y `markCompositionAsTemplate` pueden copiar árboles sin revisar la policy;
- el renderer conserva `dangerouslySetInnerHTML` para `vmx.custom.html`.

Por ello, una conexión literal sería inválida: o habilitaría campos no gobernados o bloquearía composiciones históricas completas. Este addendum sustituye esa ambigüedad por correspondencias explícitas.

## 4. Regla de identidad y compatibilidad

### 4.1 Identidad runtime

Los identificadores conceptuales de I4-0 sirven como intención contractual; no se persistirán como aliases. I4-A deberá usar exactamente el `type` registrado en Block Library y Registry.

| Concepto I4-0                 | Identidad runtime canónica I4-A       | Disposición                                                                    |
| ----------------------------- | ------------------------------------- | ------------------------------------------------------------------------------ |
| `vmx.hero`                    | `vmx.experience.hero`                 | reemplazo contractual; el `vmx.hero` histórico no se ofrece para nueva autoría |
| `vmx.rich-narrative`          | `vmx.experience.section`              | reutiliza la sección editorial oficial                                         |
| `vmx.gallery`                 | `vmx.experience.gallery`              | reutiliza la galería oficial                                                   |
| `vmx.governed.practical-info` | `vmx.experience.info-grid`            | binding gobernado; `items[].value` nunca será texto libre                      |
| `vmx.governed.trust-signals`  | `vmx.experience.institutional-badges` | binding exclusivo a Trust Registry                                             |
| `vmx.custom.html`             | `vmx.custom.html`                     | identidad conservada como `legacy_read_only`                                   |

Ningún alias conceptual será aceptado dentro de un árbol nuevo. La policy y la metadata de la Library deberán declarar las identidades runtime de la tabla anterior.

### 4.2 Catálogo histórico congelado

Un tipo registrado que no pertenezca a la allowlist I4-A podrá seguir resolviéndose por Registry para render histórico. No podrá listarse en la Library de autoría ni crear una instancia nueva.

Al guardar una composición existente, el servidor podrá aceptar un nodo no authorable únicamente cuando encuentre el mismo `id`, `type`, `version`, `config`, `i18n`, `hidden`, padre y orden relativo en el borrador anterior. Cualquier diferencia, nuevo identificador, cambio de padre, reordenamiento, traducción, duplicación o reutilización se rechaza. Esta compatibilidad no convierte el nodo en authorable.

## 5. Allowlist runtime de bloques, fields y variantes

### 5.1 `vmx.experience.hero`

- **Modo:** `authorable`.
- **Variantes:** `immersive`, `compact`, `editorial`, `cinematic`, `gallery`.
- **Editoriales:** `eyebrow`, `title`, `description`.
- **Presentación cerrada:** `variant`, `overlay`, `alignment`, `eyebrowStyle`, `overlapHeader`, `slideIntervalMs` dentro de los enums y límites del contrato oficial.
- **Media:** `mediaUrl`, `mediaAlt` y `mediaSlides` sólo desde `media.registry`; una URL escrita libremente no acredita procedencia.
- **CTA:** label editorial y destino exclusivamente como referencia `routing.canonical`.
- **No escribibles:** `contractVersion`, `source`, badges, meta, rating/live capabilities y `extensions`.

### 5.2 `vmx.experience.section`

- **Modo:** `authorable`.
- **Variantes:** `editorial`, `split`, `centered`, `quote`.
- **Editoriales:** `eyebrow`, `title`, `lead`, `body`, `attribution`, `ariaLabel`.
- **Presentación cerrada:** `variant`, `align`, `tone`.
- **Media:** `mediaUrl` y `mediaAlt` sólo desde `media.registry`.
- **CTA:** máximo dos, con destino `routing.canonical` y emphasis registrado.
- **No escribibles:** `contractVersion`, `source`, `capabilities` y `extensions`.

### 5.3 `vmx.experience.gallery`

- **Modo:** `authorable`.
- **Variantes:** `mosaic`, `grid`, `carousel`, `strip`.
- **Editoriales:** `heading`, `subheading`, `ariaLabel`, caption y alt contextual.
- **Presentación cerrada:** `variant`, `maxVisible`, `aspect` dentro de sus límites.
- **Media:** cada item debe resolver a `media.registry`; no se acepta URL, video, 360, modelo 3D, AR o UGC externo libre.
- **No escribibles:** `contractVersion`, `source`, `extensions` y capabilities no autorizadas.

### 5.4 `vmx.experience.info-grid`

- **Modo:** `governed_read_only`.
- **Variantes:** `cards`, `list`, `inline`.
- **Presentación seleccionable:** `variant`, `columns`, `ariaLabel` y heading editorial.
- **Bindings:** `operations.schedule`, `geography.location`, `commerce.price` y `commerce.availability`.
- **No escribibles:** `items[].value`, `href`, `source`, capabilities live, `contractVersion` y `extensions`.
- `source: manual` queda prohibido para horario, dirección, precio, rating o disponibilidad.

### 5.5 `vmx.experience.institutional-badges`

- **Modo:** `governed_read_only`.
- **Variantes:** `filled`, `soft`, `outline`, `icon-only`.
- **Presentación seleccionable:** `variant`, `size`, `layout`, `ariaLabel` y capabilities visuales registradas.
- **Binding:** exclusivamente `trust.badges` mediante el registry institucional existente.
- **No escribibles:** kind, slug, label material, emisor, verificación, vigencia, `programUrl`, `evidenceUrl`, `source`, `contractVersion` y `extensions`.

### 5.6 `vmx.custom.html`

- **Modo:** `legacy_read_only`.
- **Variante:** `legacy`.
- **Operación única:** `render_legacy`.
- **Prohibido:** insertar, editar, reordenar, duplicar nodo, duplicar composición, IA, traducción, reusable block, binding, template nuevo y publicación como contenido nuevo.

## 6. Normalización de superficies

La superficie se derivará server-side del `kind`/`page_type` persistido; nunca llegará como autoridad confiable desde el cliente.

| `PageKind` existente                         | Superficie I4       |
| -------------------------------------------- | ------------------- |
| `home`                                       | `home`              |
| `landing`, `campaign`, `promo`, `wedding`    | `landing`           |
| `microsite`, `institutional`, `site_section` | `institutional`     |
| `destination`, `route`                       | `destination`       |
| `region`                                     | `region`            |
| `business`, `hotel`, `restaurant`            | `business`          |
| `product`, `experience`, `event`             | `product`           |
| `marketplace`                                | `marketplace`       |
| `alux`                                       | `alux`              |
| `trip_builder`                               | `trip_builder`      |
| `ai_generated`, `custom` o valor desconocido | rechazo fail-closed |

El filtro `home` hardcoded de la Library deberá desaparecer. Visual y Professional comparten la misma policy; Professional no desbloquea HTML, fields, fuentes ni variantes prohibidas.

## 7. Normalización de roles

I4-A no crea roles. Usa el RBAC existente con esta traducción cerrada:

| `AppRole`                                 | Actor I4             | Alcance I4-A                                                          |
| ----------------------------------------- | -------------------- | --------------------------------------------------------------------- |
| `super_admin`, `admin`                    | `founder_admin`      | superficies admitidas por cada bloque                                 |
| `editor`                                  | `territorial_editor` | superficies editoriales admitidas                                     |
| `business_owner`                          | `business_author`    | sólo superficie `business`; aislamiento por entidad permanece en I4-B |
| `concierge`, `concierge_lead`, `traveler` | ninguno              | rechazo                                                               |

`reviewer_approver`, `publisher` y `system` son capacidades contractuales posteriores; I4-A no las deriva ni habilita. Si el servidor no puede determinar rol o superficie, rechaza el guardado.

## 8. Frontera server-side

La autoridad dura seguirá en `studio.functions.ts`, antes de cualquier traducción o RPC. Deberá:

1. cargar composición, `page_type`/`kind` y borrador anterior;
2. resolver actor con RBAC existente;
3. validar recursivamente tipo, versión, superficie, rol, variante, field, tipo, enum, longitud, cardinalidad, fuente y destino;
4. comprobar que nodos históricos congelados no cambiaron;
5. rechazar cualquier nueva instancia de `vmx.custom.html` o de un tipo fuera de allowlist;
6. ejecutar traducción únicamente después del primer PASS y volver a validar el árbol resultante;
7. invocar la RPC existente sólo después del segundo PASS.

La misma policy deberá proteger `saveCompositionDraft`, `duplicateComposition` y `markCompositionAsTemplate`. Las acciones UI son explicación y prevención, no autoridad de seguridad.

No se modifica ninguna RPC, tabla, RLS, migración o ruta para lograrlo.

## 9. Enlaces y embeds · SEC-07

La allowlist inicial de hosts externos para nueva autoría es exactamente vacía.

I4-A admitirá únicamente:

- referencias internas seleccionadas desde `routing.canonical`;
- assets seleccionados desde `media.registry`;
- atributos seguros generados por el renderer, nunca introducidos como HTML.

Se rechazarán `javascript:`, `data:`, `blob:`, protocolos desconocidos, URL protocol-relative, iframe, embed, script, style, event handlers, query libre y cualquier host externo. Agregar un dominio exigirá una evolución gobernada posterior; no se permitirá una variable de entorno o lista UI como bypass.

El HTML histórico queda fuera de nueva autoría y no se usa como evidencia positiva de SEC-07. Si una composición histórica requiere modificar su embed, deberá regresar a Founder Review en un lote separado.

## 13. Gate, rollback y condiciones de parada

### Entrada futura

1. base exacta idéntica a `main`;
2. pack `18.48` aprobado;
3. exactamente quince rutas;
4. PCA-2026-013 coincidente;
5. cero dependencias, lockfile, migraciones, RPC, rutas o flags nuevos;
6. fixtures y hashes reproducibles definidos.

### Salida futura

1. worktree inicialmente limpio;
2. lista exacta de rutas y cantidad `15`;
3. cero referencias prohibidas;
4. árbol candidato calculado mediante índice Git temporal;
5. un único commit y cero cambios ajenos;
6. pruebas positivas/negativas, suite local integral y GitHub Actions en PASS;
7. 07, 08 e inventario regenerados únicamente mediante el sincronizador;
8. flag vigente OFF, sin producción ni publicación.

### Rollback

Antes del merge, abandonar la rama candidata. Después de un merge autorizado, revertir el único commit. Como I4-A no cambia datos, schema, RPC, dependencias, rutas o producción, no necesita rollback de base de datos. El renderer histórico permanece intacto durante ambos estados.

### STOP

Detener y regresar a Founder Review si se requiere:

- un tipo, field, variante, fuente, rol, superficie o host no enumerado;
- modificar renderer, ruta, RPC, tabla, RLS, migración, dependencia, lockfile o flag;
- aceptar un nodo histórico sin comparación exacta server-side;
- confiar en un filtro UI como control de seguridad;
- permitir que traducción, IA, reusable blocks, duplicate o template eludan la policy;
- ampliar o reducir las quince rutas durante la implementación;
- declarar EBG-01–04 o SEC-07 sin pruebas positivas y negativas reproducibles.

## 14. Declaraciones negativas

Este addendum confirma que I4-A no necesita migraciones, dependencias, rutas públicas, RPC nuevas, activación de flags ni cambios de renderer. Tampoco autoriza producción, datos reales, Premium, Commerce, publicación, I4-B/C/D, P0, P1 o L1.
