# Commerce rules

- Online sales per business: `business_online_sales` (one row per business, written only by the admin RPC `admin_set_business_online_sales`) gates every non-experience online sale; `online-sales-rules.ts` (`businessAllowsOnlineSale`) and the SQL `business_online_sale_allows` apply the same rule to the product page button (`pagina`), Alux (`alux_pagina`), the product-enable trigger and `concierge_create_direct_sale_order`. Experiences never depend on the switch. Delivery, booking and calendar lists exist with only pilot values active. Why: one switch per business, the same answer in every channel, and room to grow without rework.
- Online sales commission: per sale type (store, pickup orders, hotels) in `platform_settings` key `commerce.online_sales.commission_bps`, suggested when approving a product; experiences and dated services keep their per-product commission. Why: the values change often and must stay admin-editable.
- Store and pickup sales (phase 2): store products are `artesanal` products with `direct_sale_stock` (NULL = unlimited), created in bulk only by the admin RPC `admin_create_store_products` and decremented by the paid-order trigger; pickup orders are multi-line `concierge_orders` built from the published carta by `commerce_create_menu_order` (`menu_item` lines), shown through `MenuOrderCart` around the official menu block only when `pedidos`+`pagina` is on. Both reuse the existing checkout. Why: one order/payment/settlement path; the carta stays the single menu source.
- Hotel nights (pilot): room types are `hotel` products (`direct_sale_stock` = rooms of that type, price per night); `commerce_request_stay` creates a `draft` order with one `hotel_night` line and `stay_status=pending_host` holding the nights 12 h, the business (or admin) answers with `commerce_decide_stay`, and a trigger blocks any payment while pending. Availability comes only from `commerce_public_stay_calendar` + `stay-calendar.ts`. Why: confirmation by the hotel avoids overbooking without channel managers, and the stay reuses the same order/payment/Portal path.
- Day calendar: every date-bound sale (hotel nights, experiences, tours, other departures) shares `RatesCalendar.tsx` over `commerce_day_calendar_manage`/`commerce_day_calendar_set`; per-day prices live in `commerce_stay_night_rates` (missing date = product base price) and blocks reuse `commerce_blackouts`; public stay calendar, `commerce_public_departures` and `commerce_booking_start` read the same per-day price. Room count per hotel type changes only via `commerce_calendar_set_rooms`. Why: one pricing/blocking authority so the traveler sees exactly what the business set, with no second system per product type.
- Carta orders: menu sections named Extras/Adicionales/Complementos/Toppings are extras (`isMenuExtraSection` mirrors SQL `menu_section_is_extra`); extras never travel alone, and each drink line may carry its own extras (`for_item`) and a short note, both written into the order line title by `commerce_create_menu_order`; store purchases add their note through `commerce_set_store_note`. Why: the business sees «Leche vegetal · para Latte» and «Nota: …» in its existing order list without a second order model.
- Table booking (Reservar mesa): enabled by the `mesas` mode of `business_online_sales` (admin only) plus `restaurant_booking_settings` with tables; availability is computed only by `restaurant_public_slots`/`_restaurant_fits` (greedy table assignment per overlapping reservation) and rechecked under an advisory lock in `restaurant_book`; reservations live in `restaurant_reservations` (RPC-only writes), whole closed days reuse `commerce_blackouts` with `product_id` NULL, billing starts off and only `admin_set_restaurant_booking_billing` changes it. The public widget (`TableBookingWidget`) renders nothing unless enabled; notices go through UNC in-app/push and the `vmx-*` WhatsApp line once per reservation (`notices_sent_at`). Why: one availability answer for page, Alux and Portal, and an untouched restaurant template when the switch is off.
- Table booking stage 2: the floor plan lives in `restaurant_booking_settings.floor_plan` (saved only via `restaurant_floor_plan_save`, which also rewrites `tables` from the plan so public availability matches it); table assignment (`restaurant_assign_table`, rejects overlaps), waitlist (`restaurant_waitlist`) and guest notes (`restaurant_guest_notes`, keyed by last 10 phone digits) are RPC-only writes for the business team; reports and guest history are computed from `restaurant_reservations` in `table-floor.ts`. Why: one reservation source, no second guest database.
- Table booking holds and self-service: picking a time creates a 5-minute `restaurant_slot_holds` row counted by `_restaurant_fits` and consumed by `restaurant_book(_hold)`; guests change or cancel only through `restaurant_manage_*` RPCs keyed by the private `manage_token` link (`/reservacion-mesa/$token`). Why: no double booking while a guest types, and no account needed to manage a reservation.
- Table zones: the public time selector uses future server-approved slots; zone buttons read only the saved floor plan, and the zone-aware overloads of the existing slots/hold/book RPCs allocate a real table under the existing lock, keeping its table id in the reservation. Why: no invented zones, duplicate times, or separate occupancy model.
- Mi Viaje table reservations: the Reservas view lists the signed-in traveler's upcoming tables via `listMyTableReservations` (RLS own rows, `user_id` set by `restaurant_book` when signed in) and links to the private manage page. Why: one reservation source shown in the trip without copying rows into orders.
- Hotel venue link: `business_venue_links` (host = hotel, venue = its restaurant/café) is read publicly only through `business_public_venues` (both businesses published) and managed only through `business_venue_link_add/remove`, which require editor access to BOTH businesses; the Portal panel and the public `HotelVenueSection` (one Tourism Card, `#reservar-mesa` anchor when booking is on, via `useHashTargetScroll`) render nothing when there is no link. Why: one approved link per pair so a hotel never claims another business's restaurant and no restaurant template changes when the feature is unused.
- Cashier screen: `/caja/$slug` signs in with a per-restaurant PIN (hash in `restaurant_booking_settings.cashier_pin_hash`, 5 failures lock 15 min) that returns a 16 h token in `restaurant_cashier_sessions`; it only reads `restaurant_cashier_board` and writes through `restaurant_cashier_seat/set` (walk-ins become `sentada` `sin_cita` reservations, freeing sets `terminada` and `ends_at=now()`), so availability stays computed by `_restaurant_fits`. Unfreed tables release themselves at `duration_minutes`. Why: staff mark tables without an admin account and without a second occupancy model; a future POS hook writes through the same RPCs.
- Soft Restaurant connector: `public/downloads/conector-softrestaurant.ps1` (+ `iniciar-conector.bat`) runs on the restaurant PC, reads open checks read-only from SQL Server (`tempcheques`, query overridable in its config) and writes only through the cashier PIN RPCs, freeing only the tables it seated. Why: browsers cannot reach a local SQL Server, and occupancy keeps a single authority.
